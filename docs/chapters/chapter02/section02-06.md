# 第六节 结构化分析

结构化分析（Structured Analysis，SA）是软件需求分析的一种传统而有效的方法，起源于20世纪70年代，主要应用于瀑布模型开发过程。它以问题分解为核心，通过自顶向下、逐步分解的方式分析系统功能。

## 6.1 结构化分析基本原理

### 6.1.1 核心思想及特点

#### 可视化表达
通过图形化建模（如DFD、0层、1层分解），帮助技术人员理解复杂业务流程。
示例：在医院挂号系统中，患者提交表单，系统验证身份并生成挂号单，过程可用数据流图清晰表示。

#### 模块化设计
将系统分解为可独立开发、测试和维护的组件，降低复杂性。适合瀑布式团队分工，确保大型软件工程的可管理性。例如，在线电子商务系统可分为用户管理、订单处理、支付处理等模块。

#### 文档规范化
生成详细的需求规格说明书（SRS），符合ISO/IEC标准，适合合同约束的项目。

### 6.1.2 结构化分析的优缺点

#### 处理需求适应性差
基于前期固定的需求定义，对于开发过程中不断变化的需求缺乏灵活性。需求变更需要重新进行DFD、数据字典等维护，成本较高。
相比，敏捷方法通过用户故事和迭代开发适应变化。

#### 难以处理复杂的对象交互
结构化分析侧重从GUI应用中的事件处理逻辑分离，用户点击按钮触发的模块间交互。
示例：电商应用的"结账"流程涉及用户界面、实时通知、库存统计等多组件协作，更适合面向对象分析（OOA）。

#### 实时系统支持不足
对时间关键型系统（如自动驾驶、实时控制、数据处理等）缺乏有效建模手段，无法满足并发时间约束。

#### 大量文档负担
在较小项目中可能不必生成完整文档（如数据字典），而采用更轻量级的方法。

## 6.2 自顶向下的分解

当面对复杂系统时，试图同时理解所有细节会导致分析错误和混乱。为了有效处理复杂性，自顶向下的分解成为一种关键技术。这种方法通过将问题逐层分解为更小、更容易管理的部分，逐步降低复杂性，使得问题变得简单而清晰。图2-10显示是对一个函数的自顶向下分解。

![自顶向下函数分解](../images/chapter02/top_down_decomposition.png)

图2-10 对一个函数的自顶向下分解

分解的基本原理是对功能进行分解的核心思想是从系统最高层次开始，不断向下深入到最详细的层次。首先，分析人员关注系统的主要功能和主要完成部分，忽略细节。然后，逐渐深入更多细节，分析子功能，直到每个部分都能被清晰地定义和实现。

其次，定义系统的外部功能和接口，只关注系统必须做什么，而不关注内部细节。中间层次将对整体系统分解为若干子系统，每个子系统完成系统的一个主要功能或模块，开始涉及系统内部的结构和交互。底层是将系统分解为最小的功能单元，直到每个部分都能被详细描述和实现。分解的层次可以根据系统的功能性、数据的复杂性和业务范围来划分。例如，在电子商务系统中，可以按照订单处理、支付处理、物流管理等功能进行分解；在客户关系系统中，可以按照客户信息、沟通信息、支持信息、数据分析进行分解；在供应链管理系统中，可以按照采购管理、生产等业务环节进行分解。通过这种分解，分析人员可以深入理解系统的细节，避免一开始就面对复杂的细节小。分解促使系统采用模块化设计，每个模块可以独立开发和测试，提高开发效率。明确的分解使得系统结构更加清晰，有助于团队成员之间的沟通和协作。

在实际软件项目中，自顶向下的分解方法广泛应用于软件需求分析与设计。例如，在开发一个智慧水利平台时，可以从顶层开始将系统分解为用户管理、水文分析、水利工程监测、决策支持等子系统。然后进一步将每个子系统分解为更详细的功能模块。通过这种逐层且有序的分解，分析人员可以更加系统地理解系统需求，确保每个部分都能被清晰地定义和实现，从而提高项目的成功率。

## 6.3 结构化分析方法

结构化分析（Structured Analysis, SA）是一种系统需求分析的方法论，旨在通过分解复杂系统为多个简单的部分，使用图形和逻辑工具帮助开发团队理解和设计系统。这种方法的核心思想是通过图形化工具（如数据流图、数据字典等）对系统的功能、数据和处理流程进行详细描述，形成系统需求规格说明书。以下是结构化分析的具体步骤：

### 6.3.1 分析现行系统（如果存在）

分析现行系统指当前正在运行的系统，可能是基于计算机的系统，也可能是人工操作的系统。首先，需要研究现行系统的具体情况，收集相关信息和数据。通过观察记录现行系统的工作流程，以及使用的工具和设备等。随后，使用图形化工具如数据流图和数据字典的形式，对现行系统进行建模。该模型反映了系统的实际运行状况，包括各个流程的操作步骤、使用的工具和设备等。例如，在一个图书馆管理系统中，现行模型可能包括图书的借出、归还流程，以及使用的计算机系统和数据库。

### 6.3.2 创建现行系统的逻辑模型

在分析完现行系统的物理模型后，需要进一步构建逻辑模型。逻辑模型关注的是系统做什么，而不是"怎么做"。通过去除物理模型中的非本质部分（如硬件设备、物理布局等），只保留系统的核心功能和业务流程。例如，在图书馆管理系统中，逻辑模型可能包括用户借阅图书的申请和处理的功能，而不涉及使用的计算机设备和操作人员。

### 6.3.3 设计目标系统的逻辑模型

目标系统指新开发或改进的系统。在构建现行系统的逻辑模型后，可以将其与目标系统进行比较，找出需要改进的部分。这些变化的部分将被处理为一个新的子流程，确定输入、输出和外部接口。通过自顶向下、逐步精细的方法详细描述这些子流程，构建目标系统的逻辑模型。例如，在图书馆管理系统中，可能需要增加一个在线预约功能，这个功能就会被设计为一个新的子流程，详细描述其输入（用户信息、图书信息）、处理（验证用户身份、检查图书可用性、生成预约）和输出（预约成功或失败的通知）。

### 6.3.4 进一步完善与优化

目标系统的逻辑模型只是一个初步方案，为了打造完整的目标系统，还需要进行一些进一步的优化。包括明确系统与应用环境、外部系统的接口、人机交互方式等问题。此外，需要解决一些在前面未详细说明的基础，如输入/输出格式、存储结构和响应时间等要求。例如，在图书馆管理系统中，可能需要详细规定未归还图书的提醒机制，以及系统在不同负载下的响应时间要求。

## 6.4 系统流程图

系统流程图（System Flowchart）是描述系统内部流程的传统工具，用于表示系统中各组成部分之间的数据流动和处理过程。它通过图形符号以清晰方式显示系统中每个操作步骤、系统间的数据输入输出和决策点，是对信息系统进行加工处理的可视化规划工具。

### 6.4.1 系统流程图的作用

系统流程图主要用于描述计算机系统操作流程，实现和系统的物理特性。它帮助分析人员在开发研究、需求分析和设计阶段了解系统的处理过程、范围和功能，作为后续系统设计提供依据。系统流程图主要应用于开发研究、需求分析和系统设计阶段。

### 6.4.2 系统流程图的符号

系统流程图由一系列图形符号组成，这些符号在不同的标准中可能略有不同，但通常包括以下几种：

**表6-1 系统流程图的符号**

| 符号 | 说明 |
|------|------|
| 处理 | 能改变数据值或位置的加工处理过程,包括模块、函数等都是处理 |
| 输入/输出 | 表示人或手工输入一数据到指定的输入设备的符号 |
| 连接符 | 指示转向图上的一个点或从图上的一个点转来,通常在同一页 |
| 跨页连接 | 指示转向另一页图或从另一页图转来 |
| 判断框 | 表示条件或分支点，指出多种可能的路径 |
| 文档 | 通常表示打印输出,也可表示该打印终端的输出结果 |
| 磁介质存储 | 表示任何形式的磁介质存储,包括磁盘、磁带和辅助存储设备 |
| 文件 | 表示输入/输出,也可表示存储在磁盘上的文件或数据库 |
| 显示 | CRT终端或类似的显示设备,可以交互人机对话,也可兼有输入功能 |
| 人工操作 | 人工处理的数据或由人工输入的数据,如手工记录 |
| 人工准备 | 人工输入的处理过程，例如，填写银行支票标签等 |
| 自动操作 | 使用设备进行的自动处理 |
| 通信连路 | 通过远程通信连路传送或接收信息 |

### 6.4.3 系统流程图示例

以下是一个在线订购系统的流程图，展示了从客户下单到订单完成的处理过程。首先，客户在系统中下单，输入与订单相关的订单信息（产品、数量）。其次，系统对订单信息进行验证，确认客户提供的信息是有效的，包括客户资料、数据格式等。当订单信息有效，系统进行库存检查，确认是否有足够商品满足订单需求。如果库存不足，系统会通知客户并提供备选方案或等待补货的选项。

如果库存足够，系统会将订单信息存储到数据库中，订单进入处理阶段。下一阶段可能包括支付处理、仓库调度、物流安排等。然后系统会生成订单确认通知，并将其发送给客户，通知客户订单已被接受和处理。客户收到确认通知，需要确认订单的正确性，一旦客户确认完毕，订单处理完成，等待发货。

## 6.5 数据流图

### 6.5.1 数据流图符号规范

数据流图（DFD）是描述系统中数据流动和转换处理过程的一种图形化工具。它使用标准化的符号表示不同的元素，包括以下几种：

1. **处理（Process）**：表示系统或系统中的一个功能或操作。通常用圆形或圆角矩形表示。处理是数据转换点，接收输入数据并生成输出数据。表示方法：用圆形（或圆角矩形）。

2. **数据流（Data Flow）**：表示数据在系统中流动的路径。这通常由带箭头的直线表示，箭头指示数据流动的方向。表示方法：用带箭头的直线。

3. **数据存储（Data Store）**：表示系统中存储的数据或信息。数据存储通常是持久的，用于数据在存储和处理之间传递。通过用开口的矩形表示。表示方法：用方括号 [ ]。

4. **外部实体（External Entity）**：表示系统外部的参与者或外部系统。通常指用户、外部数据库或其他系统。外部实体与系统交换数据进行交互。表示方法：用矩形。

### 6.5.2 构建数据流图

在绘制数据流图时，通常从系统的最高级开始，逐渐细化到更详细的层次。数据流图的绘制一般遵循以下步骤：

1. **确定系统边界**：首先定义系统的范围，明确哪些属于系统内，哪些属于外部实体。

2. **确定外部实体**：识别出与系统交互的外部实体，如用户、客户、外部系统等。

3. **识别系统的主要过程**：确定系统中涉及的主要数据处理过程。例如，对于一个在线订购系统，主要过程可能包括：接收订单、验证订单、处理付款、生成发货单等。

4. **创建数据流连接**：确定各过程之间的数据传递，创建数据流路径。确保每个数据流都从一个过程到另一个过程或数据存储的方向。

5. **标识数据存储**：确定哪些数据在系统中需要存储，用数据存储符号表示数据的保存位置。

6. **细化和完善数据流图**：根据需要将顶层数据流图继续展开，对每个过程进行细化，形成更详细的数据流图。

示例1：顶层数据流图（Level 0 DFD）：

### 6.5.3 结构化分析方法的实际应用

结构化分析（Structured Analysis）是一种通过图形化建模、过程分解和详细描述系统流程的方法，广泛应用于系统设计和开发实践中。数据流图（DFD）是结构化分析方法中的核心工具之一，主要用于描述信息系统中的数据流动和处理过程。
结构化分析方法的典型应用流程：
1. **需求收集**：通过与用户沟通确定系统的功能需求和业务流程。此时，数据流图和实体关系图等工具可以捕获系统的主要流程和数据关系。
2. **系统建模**：使用数据流图（DFD）对系统进行建模，设计顶层数据流图，然后针对需要细化的重点部分，设计子系统数据流图。通过数据流图，开发人员可以清晰地理解系统结构。
3. **过程规范**：每个数据流图中的过程都需要有对应的处理规范，描述该过程如何将输入数据转换为输出数据。通过详细的过程规范，确保系统最终的功能实现正确。
4. **数据字典的使用**：在结构化分析中，数据字典用于补充数据流图中的数据流、数据存储和其他元素的详细信息，确保数据的一致性和完整性。
5. **系统实现和验证**：在开发过程中，根据数据流图和相关文档指导开发人员构建系统。在系统测试阶段，数据流图有助于检查流程和数据流的正确性。

通过应用结构化分析方法，系统开发人员能够实现对需求的有效捕获和系统的高效设计，确保项目的顺利实施和用户需求的满足。

## 6.6 数据字典

数据字典（Data Dictionary, DD）是结构化分析方法中用于定义数据流图中各元素的详细信息的工具。它是数据流图的重要组成部分，用于提供对数据流图中的数据流、数据存储和其他图形元素的定义。数据字典的主要目的是为分析员、用户和编程人员提供一个统一的、无歧义的数据定义，确保系统中的所有元素能够被准确理解和一致使用。

数据字典通常包括数据项目、数据结构项目、数据流项目、数据存储项目和加工过程项目。数据项目是对数据流图中最小的数据单元的定义，包括名称、类型、长度、取值范围等；数据结构项目是对复合数据项的规格说明，如记录结构、数组或文件；数据流项目是对数据流中传递的数据进行说明，包括组成、来源、去向和描述；数据存储项目是对系统中存储的数据进行定义，包括组织方式、存储结构和查询要求；加工过程项目是对数据流图中的加工逻辑进行说明，包括输入、输出、使用的算法等。

在实际的数据字典中，每个项目都采用标准化的格式进行描述，例如，数据流项目可能包括如下信息：

**名称**: 订单
**别名**: 无
**描述**: 由顾客在进行购票时填写的订单信息，包含与订票相关的各种详细数据。
**来源**: 顾客
**去向**: 加工过程-检查订单
**组成**:
  订单编号 + 
  购票日期 + 
  顾客编号 + 
  地址 + 
  电话 + 
  银行卡号 + 
  预定日期 + 
  目的地 + 
  票数

**类型**: 结构化数据
**定义**:
  订单编号: 10字符
  购票日期: YYYY-MM-DD格式
  顾客编号: 8字符
  地址: 最大100字符
  电话: 11字符
  银行卡号: 16字符
  预定日期: YYYY-MM-DD格式
  目的地: 最大50字符
  票数: 整数

**取值范围**:
  订单编号: 字母和数字组成，唯一
  购票日期: 有效日期范围（例如：2025-01-01到2025-12-31）
  顾客编号: 唯一标识的数字编码
  地址: 非空，最大100字符
  电话: 11位数字，符合国家标准
  银行卡号: 16位数字，符合银行卡号格式
  预定日期: 有效日期范围
  目的地: 有效的城市或地点名称
  票数: 有效范围在1到1000

数据字典的实现可以通过手工方式或自动化工具完成。手工方式适用于小型系统的开发，而自动化方式则适用于大型系统，通常使用数据库专门的工具来创建和维护数据字典。通过数据字典，开发人员可以确保系统中的数据定义一致、准确，为软件设计、开发和测试提供可靠的基础。数据字典不仅是需求分析阶段的重要产出，也是整个软件开发过程中不可或缺的文档之一。

## 小结

本节详细介绍了结构化分析的方法和工具，包括基本原理、自顶向下的分解、结构化分析方法、系统流程图、数据流图和数据字典。

结构化分析是一种传统而有效的软件需求分析方法，通过自顶向下、逐步分解的方式分析系统功能。其核心特点包括可视化表达、模块化设计和文档规范化，适合于瀑布式开发模型。

自顶向下的分解是处理复杂系统的有效方法，通过将问题逐层分解为更小、更容易管理的部分，逐步降低复杂性。这种方法从系统最高层次开始，不断向下深入到最详细的层次，使得系统结构更加清晰，有助于团队成员之间的沟通和协作。

结构化分析方法的具体步骤包括分析现行系统、创建现行系统的逻辑模型、设计目标系统的逻辑模型以及进一步完善与优化。系统流程图和数据流图是结构化分析中的重要工具，用于描述系统内部流程和数据流动。数据字典则是对数据流图中各元素的详细定义，确保系统中的所有元素能够被准确理解和一致使用。

通过应用结构化分析方法，系统开发人员能够实现对需求的有效捕获和系统的高效设计，确保项目的顺利实施和用户需求的满足。
