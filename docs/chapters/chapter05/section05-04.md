# 5.4 数据库持久化技术

数据库持久化技术是现代企业级应用的核心基础设施，承担着数据存储、查询、更新和管理的关键职能。在Spring生态中，从传统JDBC到现代Spring Data JPA的演进，每一次技术革新都在简化开发复杂度的同时提升了系统性能和可维护性。

!!! info "本节学习重点"
    
    本节将系统介绍**数据访问层设计**、**Spring Data JPA核心机制**、**事务管理与数据一致性**和**业务数据建模实践**

## 5.4.1 数据访问层设计模式

### 传统JDBC与现代ORM对比

不同的数据访问技术在开发效率、性能表现和维护成本方面存在显著差异：

| 对比维度 | 传统JDBC | ORM框架 | Spring Data JPA |
|---------|----------|---------|-----------------|
| **开发效率** | 低，大量样板代码 | 中等，需要配置映射 | 高，约定优于配置 |
| **学习成本** | 中等，SQL基础 | 高，ORM概念复杂 | 中等，基于约定 |
| **性能控制** | 精确控制 | 框架优化 | 智能优化 |
| **维护成本** | 高，手动维护 | 中等，配置维护 | 低，自动化程度高 |

### Repository模式核心价值

Repository模式将数据访问逻辑封装在专门的存储库类中，为业务层提供统一的数据操作接口：

**设计优势：**
- **抽象化**：隐藏具体的数据存储细节
- **可测试性**：便于模拟和单元测试
- **职责分离**：数据访问与业务逻辑分离
- **一致性**：提供标准化的数据操作接口

**基本使用模式：**

```java
@Repository
public interface UserRepository extends JpaRepository<User, Long> {
    // 方法名查询约定
    Optional<User> findByUsername(String username);
    
    // 自定义查询
    @Query("SELECT u FROM User u WHERE u.department = :dept")
    List<User> findByDepartment(@Param("dept") String department);
}
```

## 5.4.2 Spring Data JPA核心机制

### 实体映射与关系管理

JPA实体映射是整个持久化框架的基础，通过注解声明式地定义实体与数据库的映射关系：

**核心映射注解：**

| 注解类型 | 功能说明 | 使用场景 |
|---------|----------|----------|
| **@Entity** | 标识JPA实体类 | 所有持久化实体 |
| **@Table** | 指定数据库表名 | 自定义表名和约束 |
| **@Id** | 标识主键字段 | 每个实体必需 |
| **@GeneratedValue** | 主键生成策略 | 自动生成主键值 |
| **@Column** | 字段映射配置 | 自定义字段属性 |

!!! example "完整示例代码"
    JPA实体映射示例：`examples/JPAEntityDemo.java`

**关系映射策略：**

| 关系类型 | 注解 | 加载策略 | 使用原则 |
|---------|------|----------|----------|
| **一对多** | `@OneToMany` | LAZY（推荐） | 避免N+1查询问题 |
| **多对一** | `@ManyToOne` | EAGER（默认） | 合理控制关联深度 |
| **多对多** | `@ManyToMany` | LAZY（推荐） | 考虑中间表设计 |
| **一对一** | `@OneToOne` | EAGER（默认） | 注意级联操作 |

### 查询构建与性能优化

Spring Data JPA提供了多种查询构建方式，满足不同复杂度的查询需求：

**查询方式层次：**

```
简单查询 → 方法名约定（findByUsername）
    ↓
复杂查询 → @Query JPQL（灵活查询语言）
    ↓
性能查询 → 原生SQL（数据库特定优化）
    ↓
动态查询 → Criteria API（程序构建查询）
```

!!! example "完整示例代码"
    Repository查询示例：`examples/JPARepositoryDemo.java`

**查询优化策略：**

| 优化方向 | 技术手段 | 适用场景 |
|---------|----------|----------|
| **分页查询** | `Pageable`接口 | 大数据集查询 |
| **投影查询** | DTO投影 | 只需要部分字段 |
| **批量查询** | `@Query`批量操作 | 大批量数据处理 |
| **缓存查询** | `@QueryHints` | 重复查询场景 |

### 生命周期回调机制

JPA实体支持生命周期回调，允许在特定时机执行自定义逻辑：

**回调注解时机：**

```mermaid
graph LR
    A[@PrePersist] --> B[持久化前]
    C[@PostPersist] --> D[持久化后]
    E[@PreUpdate] --> F[更新前]
    G[@PostUpdate] --> H[更新后]
    I[@PreRemove] --> J[删除前]
    K[@PostRemove] --> L[删除后]
```

**典型应用场景：**
- **审计功能**：自动记录创建时间、修改时间
- **数据验证**：持久化前的业务规则检查
- **状态管理**：自动设置默认状态值
- **事件发布**：实体变化时发布域事件

## 5.4.3 事务管理与数据一致性

### 声明式事务管理

Spring的声明式事务管理通过`@Transactional`注解提供了强大而灵活的事务控制能力：

**事务属性配置：**

| 属性 | 说明 | 常用值 |
|------|------|--------|
| **propagation** | 事务传播行为 | REQUIRED, REQUIRES_NEW |
| **isolation** | 事务隔离级别 | READ_COMMITTED, REPEATABLE_READ |
| **rollbackFor** | 回滚异常类型 | Exception.class |
| **readOnly** | 只读事务 | true/false |
| **timeout** | 事务超时时间 | 秒数 |

**基本使用模式：**

```java
@Transactional(rollbackFor = Exception.class)
public Order processOrder(OrderRequest request) {
    // 1. 数据验证
    // 2. 业务处理  
    // 3. 数据保存
    // 异常时自动回滚
}
```

### 事务传播行为

事务传播行为定义了方法调用时如何处理已存在的事务：

| 传播行为 | 说明 | 使用场景 |
|---------|------|----------|
| **REQUIRED** | 加入现有事务或创建新事务 | 默认行为，适合大多数场景 |
| **REQUIRES_NEW** | 始终创建新事务 | 独立操作，如审计日志 |
| **MANDATORY** | 必须在现有事务中执行 | 强制事务环境 |
| **SUPPORTS** | 支持但不要求事务 | 查询操作 |

!!! example "完整示例代码"
    事务管理完整示例：`examples/TransactionDemo.java`

### 分布式事务处理

企业级应用经常需要处理跨多个数据源或外部系统的分布式事务：

**分布式事务挑战：**
- **数据一致性**：跨系统的ACID特性保证
- **性能影响**：分布式协调的延迟成本
- **故障恢复**：部分失败时的补偿机制
- **系统复杂性**：事务协调器的引入

**解决方案对比：**

| 方案 | 复杂度 | 性能 | 一致性 | 适用场景 |
|------|--------|------|--------|----------|
| **2PC两阶段提交** | 高 | 低 | 强一致 | 强一致性要求 |
| **补偿事务（Saga）** | 中 | 中 | 最终一致 | 业务允许补偿 |
| **事件驱动** | 中 | 高 | 最终一致 | 异步处理场景 |

## 5.4.4 业务数据建模实践

### 实体设计原则

良好的实体设计需要平衡业务表达力、性能和可维护性：

**设计原则：**

| 原则 | 说明 | 实现方法 |
|------|------|----------|
| **单一职责** | 每个实体专注特定业务概念 | 合理拆分实体 |
| **领域驱动** | 实体反映业务领域模型 | 业务语言建模 |
| **性能考虑** | 平衡关联关系与查询效率 | 合理使用懒加载 |
| **版本管理** | 支持并发控制和审计 | 乐观锁和审计字段 |

### 复杂关联关系设计

企业应用中的实体关系往往比较复杂，需要仔细设计以确保数据完整性和查询性能：

**关系设计策略：**

```
用户(User) 1:N 订单(Order) N:M 产品(Product)
    ↓           ↓              ↓
  角色映射    订单详情        分类管理
    ↓           ↓              ↓
多级权限     价格历史        库存管理
```

**性能优化考虑：**
- **索引策略**：根据查询模式设计索引
- **分区表**：按时间或业务维度分区
- **读写分离**：查询与更新操作分离
- **缓存策略**：合理使用一级和二级缓存

### 数据完整性保障

通过多层次的约束和验证机制确保数据质量：

**约束层次：**

| 层次 | 约束类型 | 实现方式 |
|------|---------|----------|
| **数据库层** | 主键、外键、唯一约束 | DDL约束 |
| **实体层** | JPA验证注解 | `@NotNull`, `@Size` |
| **业务层** | 业务规则验证 | 自定义验证器 |
| **应用层** | 输入验证和转换 | Controller验证 |
