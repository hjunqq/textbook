\chapter{后端开发技术}

\paragraph*{学习目标}

通过本章学习，学生应能够：
\begin{enumerate}
\item 说明智慧水利后端的职责，设计符合HTTP语义的RESTful API；
\item 使用Spring Boot组织配置、依赖注入、控制器与服务；
\item 使用Jakarta Persistence完成实体映射、Repository访问和事务处理；
\item 使用Spring Security 6与JWT实现基本认证和授权；
\item 区分进程内事件与跨服务消息，并使用消息队列实现可靠解耦；
\item 通过缓存、分页、日志与指标改善服务性能和可运维性。
\end{enumerate}

\paragraph*{引言}

智慧水利后端负责接入监测数据、执行业务规则、维护一致性并向前端提供接口。本章统一采用Java 17、Spring Boot 3.2+、Spring Security 6、Jakarta Persistence 3.1与Jakarta Servlet 6.x；JWT示例按jjwt 0.11+接口编写。分布式事务和领域驱动设计作为选学内容，不作为首次后端课程的前置要求。

\section{后端服务与REST接口概述}

后端位于用户界面与数据资源之间，承担身份校验、业务计算、持久化、审计和系统集成。典型请求链路为“浏览器或设备网关—控制器—应用服务—Repository—数据库”。控制器只处理协议转换和输入校验，业务规则放在服务层，数据访问集中在Repository；若进一步拆分为微服务，还需显式管理边界、版本和分布式失败\cite{newman2021}。

HTTP方法的基本语义见表\ref{tab:http-methods}。接口设计不仅要返回数据，还要正确使用状态码：创建成功通常返回201，参数无效返回400，未认证返回401，无权限返回403，资源不存在返回404，服务器异常返回500。

表\ref{tab:http-methods}中的幂等性描述的是同一请求重复执行后的资源最终状态，而不是网络层只发送一次。值班员在弱网环境下可能重复点击“提交处置”，客户端可以为一次业务操作生成\texttt{Idempotency-Key}，服务端以“用户+键+资源类型”建立唯一约束并缓存第一次响应；这样重试不会创建两条处置单。\texttt{POST}本身通常不是幂等的，只有把业务键、去重窗口和冲突响应写进契约，才能把它安全地用于设备重投。

图\ref{fig:ch05-request-chain}把一次监测值写入拆成五个可测试边界：控制器负责把JSON转换为命令并拒绝格式错误，应用服务检查测站状态、质量码和时间窗口，Repository执行参数化查询，数据库保证约束与索引。任何一层都不应越过下一层直接修改另一层的内部状态；例如控制器不拼接SQL，Repository不决定预警业务规则。

资源路径使用名词，例如\texttt{/api/stations/ST-01/readings}；筛选条件放入查询参数，例如\texttt{?from=...\&to=...}。设备协议接入属于边缘网关职责，本章不展开Modbus或MQTT细节。

资源建模先回答“系统管理的对象是什么”。测站是稳定资源，监测读数是按时间追加的子资源，告警处置单是具备状态迁移的业务资源。查询最新读数可以使用\texttt{GET /api/stations/ST-01/readings/latest}，查询时间范围使用\texttt{GET /api/stations/ST-01/readings?from=...\&to=...}；创建一条读数使用\texttt{POST /api/readings}，请求体包含测站 ID、采样时间、数值、单位和质量码。路径表达资源层级，查询参数表达视图条件，业务动作只有在无法用资源状态表达时才使用动词，例如\texttt{POST /api/alerts/AL-01/acknowledge}。

分层依赖方向应从外向内收敛：Controller 依赖 Application Service，Service 依赖领域对象和 Repository 接口，Repository 的具体实现依赖 PostgreSQL、PostGIS 或 TimescaleDB。领域对象不依赖 HTTP、JSON 和 Spring 注解，便于在单元测试中用内存对象验证规则。若把数据库实体直接作为响应体，内部字段、懒加载关系和审计信息可能泄露到外部契约；DTO 映射应在控制器或应用服务边界完成，并为时间、单位和质量码提供稳定格式。

\label{lst:ch05-rest-layer}
\begin{lstlisting}[language=Java,caption={分层 REST 查询：DTO、服务与仓储接口}]
public record LatestReadingResponse(
        String stationId, double level, String unit,
        Instant measuredAt, String quality) {}

public interface ReadingQueryRepository {
    Optional<WaterReading> findLatest(String stationId);
}

@Service
public class ReadingQueryService {
    private final ReadingQueryRepository repository;

    public ReadingQueryService(ReadingQueryRepository repository) {
        this.repository = repository;
    }

    @Transactional(readOnly = true)
    public LatestReadingResponse latest(String stationId) {
        WaterReading reading = repository.findLatest(stationId)
                .orElseThrow(() -> new EntityNotFoundException("测站无读数"));
        return new LatestReadingResponse(reading.stationId(), reading.level(),
                reading.unit(), reading.measuredAt(), reading.quality());
    }
}
\end{lstlisting}

清单\ref{lst:ch05-rest-layer}用只读事务包住查询，并把实体转换为响应 DTO；它没有把数据库实现类型暴露给控制器。查询结果为空时抛出领域可识别的异常，由统一异常处理器转换为404，客户端可以据此显示“暂无读数”或提示测站编号，而不是把空对象误当作水位为零。

写入接口要把协议校验、业务校验和持久化顺序写清。协议层检查必填字段、数值格式和时间字符串，应用服务检查测站是否存在、采样时间是否落在允许窗口、质量码是否允许参与计算，Repository 在事务中保存记录。创建成功返回\texttt{201 Created}并在\texttt{Location}头给出新资源地址；重复的幂等键返回第一次创建的响应或\texttt{409 Conflict}，不能静默创建第二条记录。

\label{lst:ch05-rest-write}
\begin{lstlisting}[language=Java,caption={监测值写入：POST、校验与201 Location}]
public record CreateReadingRequest(
        @NotBlank String stationId,
        @NotNull @DecimalMin("0.0") @DecimalMax("50.0") BigDecimal level,
        @NotBlank String unit,
        @NotNull Instant measuredAt,
        @NotBlank String quality) {}

@RestController
@RequestMapping("/api/readings")
public class ReadingCommandController {
    private final ReadingCommandService service;

    public ReadingCommandController(ReadingCommandService service) {
        this.service = service;
    }

    @PostMapping
    ResponseEntity<ReadingResponse> create(
            @Valid @RequestBody CreateReadingRequest request,
            @RequestHeader(value = "Idempotency-Key", required = false) String key) {
        WaterReading saved = service.create(request, key);
        URI location = URI.create("/api/readings/" + saved.id());
        return ResponseEntity.created(location).body(ReadingResponse.from(saved));
    }
}
\end{lstlisting}

这里使用\texttt{BigDecimal}表达水位，避免用\texttt{double}承载边界校验时出现二进制浮点舍入误差；服务内部仍可按明确规则转换为数据库数值类型。\texttt{@Valid @RequestBody}只负责触发Bean Validation，诸如“测站属于当前工程”“时间不得早于上一条记录”等跨字段规则必须在服务层再次检查。控制器接收可选的幂等键，但不负责保存去重记录，去重状态由服务层和数据库唯一约束共同保证。

分页、排序和过滤也要形成稳定的 URL 契约。\texttt{page}从0开始还是从1开始必须在全书统一；本章示例采用从0开始的\texttt{page}、正数\texttt{size}，排序使用\texttt{sort=measuredAt,desc}，过滤使用\texttt{stationId}、\texttt{quality}和时间范围。服务端限制\texttt{size}上限，拒绝未知排序字段，返回\texttt{content}、\texttt{page}、\texttt{size}、\texttt{totalElements}和\texttt{totalPages}，这样前端可以显示总页数而不是用当前页长度猜测。

游标分页适合持续追加的时序读数：客户端携带上一页最后一条记录的\texttt{measuredAt,id}，服务端按联合索引向后查找，避免高页码\texttt{OFFSET}扫描大量历史数据。游标应视为不透明字符串，不能让客户端自行修改时间边界；接口文档还要说明读数在分页期间追加时的排序稳定性。报表导出属于异步任务时，使用任务资源返回\texttt{202 Accepted}，由客户端轮询任务状态，而不是让一次 HTTP 请求长时间占用连接。

服务发现与微服务边界必须以业务能力为中心。数据采集、读数查询、预警评估和通知可以是不同服务，但每个服务拥有明确的数据所有权和 API 契约；拆分不是把每个类都部署成独立进程。开发环境可用配置文件把逻辑服务名映射到固定地址，生产环境再接入服务注册与发现组件、健康检查和负载均衡。业务代码只依赖接口客户端，不能把某个注册中心的注解散落到领域层，这样更换实现时只需调整基础设施配置。

跨服务调用要显式处理超时、重试和降级。查询测站详情可以在短超时后返回缓存快照，并在界面标注数据时间；写入监测值则不能因为重试而重复落库，应把请求 ID 和幂等键贯穿网关、服务日志与数据库。链路追踪至少传递\texttt{traceId}和\texttt{requestId}，错误响应包含可定位的错误码而不暴露内部堆栈。服务之间若共享 PostgreSQL 表，边界会失去意义，应改为通过版本化 API 或消息事件交换数据。

API 版本化需要在兼容性和演进速度之间作出可审计的选择。对外公开的水利平台接口可以采用路径版本\texttt{/api/v1/stations}，在字段增加时保持旧字段语义不变；删除字段、改变单位或改变时间时区都属于破坏性变更，应发布\texttt{v2}并给出迁移窗口。版本号不应随着每次修复递增，补丁修复和兼容字段增加可以通过文档和变更日志说明。响应体可带\texttt{Deprecation}和\texttt{Sunset}提示，让调用方在停止旧版本前完成升级。

错误响应应同时满足机器可判断和人可理解。建议统一包含\texttt{type}、\texttt{title}、\texttt{status}、\texttt{code}、\texttt{detail}和\texttt{traceId}，其中\texttt{code}使用稳定枚举，\texttt{detail}只提供当前请求的上下文。参数错误可以按字段返回多个问题，资源不存在包含资源类型和业务 ID，权限失败不透露资源是否真实存在。日志中的\texttt{traceId}与响应中的值一致，运维人员可以从一次值班员操作追到网关、服务和数据库查询。

幂等键的生命周期要覆盖消息最大重投和人工重试周期。服务端保存键、请求摘要、响应状态和过期时间；同一个键携带不同请求体时返回冲突，防止客户端误把一个键当作通用令牌。数据库唯一约束是最后一道防线，应用层缓存只用于快速返回，不能替代约束。处置单的状态迁移也要有唯一规则，例如只有\texttt{OPEN}可以变为\texttt{ACKNOWLEDGED}，重复确认返回当前状态而不是再次产生副作用。

分页查询需要稳定排序，否则实时读数追加时会出现重复或漏项。排序字段后追加唯一 ID 作为 tie-breaker；服务端在响应中回显实际排序方向和时间区间，客户端翻页时携带同一条件。导出任务和大范围历史查询应限制最大时间跨度，超过阈值改为异步任务并在完成后提供下载地址。对外接口还应设置速率限制和请求体大小上限，避免错误客户端占满数据库连接。

服务发现的健康检查至少分为进程存活、依赖可达和业务可用三类。进程存活用于重启异常实例，依赖可达检查数据库、Redis 和 Kafka 连接，业务可用则验证关键表结构、时序写入权限和预警规则加载。网关路由切换时先摘除不健康实例，再等待正在处理的请求完成；客户端重试只针对明确的瞬态错误，写入请求必须携带幂等键。通过这些约束，微服务边界才能在故障时保持数据一致和可观察。
接口文档还应给出示例请求、示例响应、错误码和限流规则，并在每次版本发布时同步更新 OpenAPI 描述；值班员和前端开发者据此可以复现问题、核对字段单位并确认兼容范围。

\section{Spring Boot企业级开发基础}

Spring Boot通过约定、自动配置和Starter依赖减少基础配置。自动配置会依据类路径、配置属性和已有Bean选择合适组件，但开发者仍应理解其条件，避免把“自动”误解为“不可控”。推荐目录如下：

\subsection{起步依赖与自动配置的边界}

起步依赖是一组经过验证的依赖坐标，目的是让项目以一致的版本组合获得 Web、验证、JPA、PostgreSQL 和 Actuator 能力。它不是一个运行时服务，也不会替业务代码决定领域规则；Maven 解析依赖树后，Spring Boot 才根据类路径中的类和配置条件创建自动配置 Bean。排查启动问题时，应先查看依赖树和条件评估报告，再决定是补充依赖、修改配置还是排除某项自动配置。

\label{lst:ch05-boot-dependencies}
\begin{lstlisting}[language=Java,caption={Spring Boot 3.2 起步依赖与版本管理}]
<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>3.2.12</version>
</parent>
<properties>
  <java.version>17</java.version>
</properties>
<dependencies>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-web</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-validation</artifactId>
  </dependency>
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>
  </dependency>
  <dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>
    <scope>runtime</scope>
  </dependency>
</dependencies>
\end{lstlisting}

清单\ref{lst:ch05-boot-dependencies}锁定 Java 17 和 Spring Boot 3.2 基线，依赖版本由父 POM 的依赖管理统一维护。PostgreSQL 驱动只在运行时需要，编译阶段依赖 JDBC 抽象；若后续接入 PostGIS 或 TimescaleDB，仍以 PostgreSQL 连接为基础，在数据库迁移脚本中启用扩展。生产项目应提交锁定的 Maven Wrapper 版本，构建机使用\texttt{./mvnw}而不是依赖本地 Maven 的偶然版本。

自动配置的关键是条件注解：类路径存在某个类、容器中尚未有同类型 Bean、配置属性满足条件时，配置类才会生效。自定义 Bean 会改变“缺少 Bean”条件的结果，因此添加一个数据源或消息转换器可能使默认配置退让。开发者应把覆盖点写成显式配置，并在启动日志中记录生效的 Profile 和关键连接信息（密码保持隐藏），避免把自动配置当作不可追踪的黑盒。

\subsection{application.yml 与 Profile 多环境}

配置文件按环境拆分，公共配置放在\texttt{application.yml}，开发、测试和生产差异分别放在\texttt{application-development.yml}、\texttt{application-test.yml}和\texttt{application-production.yml}。启动时使用\texttt{SPRING\_PROFILES\_ACTIVE}选择 Profile，敏感值通过环境变量或密钥管理器注入。Profile 只表达环境差异，不应把业务阈值复制成多套；清源水库的工程参数仍以第8章 8.1 参数表为唯一来源。

\label{lst:ch05-profile-config}
\begin{lstlisting}[language=YAML,caption={多环境配置与外部化密钥}]
# application.yml：所有环境共享的安全默认值
spring:
  application:
    name: water-reading-service
  jpa:
    open-in-view: false
  profiles:
    default: development

# application-development.yml
spring:
  datasource:
    url: ${DB_URL:jdbc:postgresql://localhost:5432/water}
    username: ${DB_USER:water_app}
    password: ${DB_PASSWORD:}
security:
  jwt:
    issuer: ${JWT_ISSUER:water-platform-dev}

# application-production.yml
spring:
  config:
    activate:
      on-profile: production
  jpa:
    hibernate:
      ddl-auto: validate
security:
  jwt:
    secret: ${JWT_SECRET_BASE64}
    issuer: ${JWT_ISSUER}
\end{lstlisting}

清单\ref{lst:ch05-profile-config}把生产环境的 JWT 密钥和发行者设为必填外部变量，缺少变量时让应用在启动阶段失败，而不是运行到认证请求才发现\texttt{issuer}为空。生产环境使用\texttt{ddl-auto: validate}只校验表结构，建表和扩展由版本化迁移脚本完成；开发环境可以使用\texttt{update}辅助实验，但不得把它作为生产建表策略。配置审计应检查 Profile 是否被正确激活、数据库 URL 是否指向允许的网络段和日志是否遮蔽密码。

\subsection{依赖注入与 Bean 生命周期}

控制反转把对象创建、依赖组装和销毁交给 Spring 容器；依赖注入则描述组件如何获得所需协作者。构造器注入能保证对象创建后依赖完整，字段注入会隐藏依赖并增加测试难度。一个 Bean 通常经历实例化、依赖注入、\texttt{@PostConstruct}初始化、投入使用和\texttt{@PreDestroy}销毁阶段；连接池、线程池和订阅应在对应生命周期内建立和关闭。

\label{lst:ch05-di-lifecycle}
\begin{lstlisting}[language=Java,caption={构造器注入与 Bean 生命周期}]
@Configuration
class WaterInfrastructureConfig {
    @Bean(destroyMethod = "close")
    ScheduledExecutorService refreshExecutor() {
        return Executors.newScheduledThreadPool(2);
    }
}

@Service
class StationRefreshService {
    private final StationRepository repository;
    private final ScheduledExecutorService executor;
    private ScheduledFuture<?> task;

    StationRefreshService(StationRepository repository,
                          ScheduledExecutorService executor) {
        this.repository = repository;
        this.executor = executor;
    }

    @PostConstruct
    void start() {
        task = executor.scheduleAtFixedRate(
                repository::refreshLatest, 0, 30, TimeUnit.SECONDS);
    }

    @PreDestroy
    void stop() {
        if (task != null) task.cancel(true);
    }
}
\end{lstlisting}

清单\ref{lst:ch05-di-lifecycle}展示了基础设施 Bean 与业务服务的依赖方向。调度器由配置类创建并统一销毁，服务只依赖接口和执行器；测试时可以注入假的\texttt{StationRepository}和单线程执行器，验证刷新是否按预期发生。定时任务中的异常要被捕获并记录，否则一次未处理异常可能停止后续刷新；任务间隔还要结合数据库连接池容量和监测数据的时效要求确定。

Bean 的作用域也影响生命周期。单例适合无状态服务和连接池，原型适合每次创建独立对象，请求作用域只在 Web 请求中使用。把请求上下文注入单例时，要通过代理或显式参数传递，不能把上一次请求的测站 ID 保存到共享字段。配置属性 record 采用构造器绑定，必须通过\texttt{@EnableConfigurationProperties}或\texttt{@ConfigurationPropertiesScan}注册；仅在 record 上写注解而没有启用扫描，容器不会创建可注入的\texttt{JwtProperties}。

工程目录应与依赖方向一致：\texttt{controller}只依赖\texttt{service}，\texttt{service}依赖领域对象和仓储接口，\texttt{repository}适配 PostgreSQL/PostGIS/TimescaleDB，\texttt{config}集中放安全、序列化和外部客户端。测试代码按同样的包结构组织，配置文件分为测试 Profile 和生产 Profile，避免在测试中意外连接真实清源水库数据库。

\subsection{自动配置诊断与启动契约}

当应用启动失败时，先区分“没有 Bean”“Bean 有多个候选”“配置属性缺失”和“外部依赖不可达”四类原因。开启条件评估报告后，可以看到某个自动配置类为何匹配或未匹配；例如缺少 PostgreSQL 驱动会使数据源自动配置跳过，存在两个相同类型的 Repository 实现会触发歧义。解决问题的顺序应是检查依赖树、读取有效 Profile、核对环境变量、最后才考虑排除自动配置。直接添加随机注解可能掩盖根因，使后续环境再次失败。

启动日志是部署契约的一部分。应用应输出应用名、版本、激活的 Profile、数据库主机（不含密码）、消息主题和健康检查地址；配置值按敏感级别脱敏，JWT 密钥只输出长度或摘要。容器编排系统在收到健康检查前不应把实例加入负载均衡，数据库迁移完成后才允许读取和写入请求。启动阶段如果发现 issuer、数据库 URL 或关键业务参数缺失，应立即失败并给出变量名，而不是使用空字符串继续运行。

配置属性 record 可以集中表达一组强相关参数，并通过 Bean Validation 在启动时校验。发行者不能为空，超时时间必须为正数，数据库连接池大小应有上限。校验失败时应用不会进入可服务状态，运维人员可以在部署日志中定位具体字段。配置对象只负责承载值，密钥轮换、令牌撤销和环境权限仍由安全组件完成，避免把认证逻辑塞进 YAML 解析器。

\label{lst:ch05-config-validation}
\begin{lstlisting}[language=Java,caption={配置属性注册与启动校验}]
@ConfigurationProperties(prefix = "security.jwt")
@Validated
public record JwtProperties(
        @NotBlank String secret,
        @NotBlank String issuer,
        @Min(60) @Max(86_400) long accessSeconds,
        @Min(300) @Max(2_592_000) long refreshSeconds) {}

@Configuration
@EnableConfigurationProperties(JwtProperties.class)
class SecurityPropertiesConfig {}
\end{lstlisting}

清单\ref{lst:ch05-config-validation}把配置错误前移到启动阶段，并明确访问令牌和刷新令牌的有效期范围。生产值由密钥管理器注入，配置文件只保留变量占位符；测试可以提供一组短有效期值验证刷新逻辑，但不应把测试密钥复制到生产 Profile。若项目使用\texttt{@ConfigurationPropertiesScan}，可以在启动类统一开启扫描；两种注册方式选择其一即可，重复注册会造成 Bean 名称冲突。

\subsection{Bean 作用域、代理与资源释放}

单例 Bean 在应用上下文中只有一个实例，适合无状态服务、Repository 和连接池；它的字段必须线程安全，不能保存某个请求的测站 ID 或当前用户。请求作用域 Bean 每次 HTTP 请求创建，适合请求追踪信息；原型 Bean 每次注入时创建，适合短生命周期的可变对象。把请求作用域对象注入单例时，Spring 使用代理延迟解析当前请求，测试时则要显式建立请求上下文。

生命周期回调要与资源类型匹配。数据库连接池和线程池由配置类创建，使用\texttt{destroyMethod}或\texttt{@PreDestroy}关闭；消息消费者在应用停止时先停止接收，再等待正在处理的消息完成；WebSocket 和定时刷新在组件或服务销毁时取消。若把资源创建写在构造器里而没有对应释放，容器重启和测试重复启动会留下线程、文件句柄或网络连接。

代理机制还影响\texttt{@Transactional}、\texttt{@Async}和\texttt{@Cacheable}。这些注解通过代理拦截外部调用，同类内部使用\texttt{this.method()}绕过代理，因此不会获得事务、异步或缓存行为。解决方案是把不同边界拆到另一个 Bean，或在确有必要时使用编程式模板；不要通过反射强行调用代理。代码评审应把注解所在方法的调用路径写进测试，确保“看起来有注解”与“运行时真的生效”一致。

\subsection{工程骨架的测试切片}

工程骨架搭好后，应尽早验证各层能否独立启动。\texttt{@WebMvcTest}只加载控制器和 MVC 基础设施，适合检查 JSON、状态码和参数校验；\texttt{@DataJpaTest}加载实体、Repository 和事务测试数据库，适合验证查询与索引；完整的\texttt{@SpringBootTest}才会装配安全、消息和外部客户端。测试 Profile 使用独立数据库或容器，禁止依赖开发机正在运行的 PostgreSQL 实例。

配置测试至少覆盖三种情况：合法 Profile 能启动并读取 issuer；缺少 JWT 密钥时启动失败；生产 Profile 的\texttt{ddl-auto}为\texttt{validate}且不会自动改表。依赖注入测试用假的 Repository 和时钟替换真实实现，验证刷新任务、超时和资源释放；集成测试再验证真实 PostgreSQL、Redis 或 Kafka 的连接。这样的分层测试能在代码进入控制器之前发现配置绑定和 Bean 生命周期问题。

目录结构还应服务于模块边界。\texttt{common}只放真正跨模块的值对象和错误码，不能把所有工具类都塞进去；\texttt{api}只放外部 DTO 和客户端契约，\texttt{domain}不依赖 Spring Web；数据库迁移文件按版本命名并与发布记录关联。新增预警服务时，先复制边界和测试结构，再决定是否拆分进程，避免目录先于业务边界膨胀。
每个模块还应提供自己的 README，写明启动 Profile、依赖的外部服务、健康检查和测试命令；新成员按文档即可在隔离环境复现启动过程，减少“只在某台机器上可用”的隐性配置。
文档还应列出本地开发所需的端口、初始化命令和清理方式，保证测试结束后不会遗留后台进程。

\label{lst:ch05-http}
\begin{lstlisting}[language=Java,caption={HTTP方法与资源语义}]
src/main/java/com/example/water/
  controller/   # HTTP适配
  service/      # 用例与事务边界
  repository/   # 数据访问
  domain/       # 实体和值对象
  config/       # 安全与基础设施配置
src/main/resources/application.yml
\end{lstlisting}

配置应从代码中分离，并可被环境变量覆盖。密钥不得写入版本库。

\label{lst:ch05-application}
\begin{lstlisting}[language=YAML,caption={Spring Boot应用入口与JWT配置}]
spring:
  datasource:
    url: ${DB_URL:jdbc:postgresql://localhost:5432/water}
    username: ${DB_USER:water_app}
    password: ${DB_PASSWORD}

  jwt:
    secret: ${JWT_SECRET_BASE64}
    issuer: ${JWT_ISSUER:water-platform}
\end{lstlisting}

依赖注入优先使用构造器，使依赖明确并便于测试。控制器把DTO交给服务，不直接访问数据库。

@RestController

class StationController {

\section{Jakarta Persistence与事务管理}

\subsection{实体映射与Repository基础}

先建立实体映射与Repository，再讨论事务边界。实体标识应稳定；接口层DTO与持久化实体分离，避免数据库结构直接成为外部契约。

\label{lst:ch05-jpa-entity}
\begin{lstlisting}[language=Java,caption={Jakarta实体映射}]
@Entity
@Table(name = "water_reading")
class WaterReading {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    @Column(nullable = false) private String stationId;
    @Column(nullable = false) private double level;
    @Column(nullable = false) private Instant measuredAt;

    protected WaterReading() {}
    WaterReading(String stationId, double level, Instant measuredAt) {
        this.stationId = stationId;
        this.level = level;
        this.measuredAt = measuredAt;
    }
}

interface WaterReadingRepository extends JpaRepository<WaterReading, Long> {
    Optional<WaterReading> findFirstByStationIdOrderByMeasuredAtDesc(String id);
}
\end{lstlisting}

Repository提供基本数据访问，服务层决定一次用例需要哪些读写。查询列表时应分页，避免把多年监测记录一次加载到内存。

\subsection{事务边界与传播}

\texttt{@Transactional}通常标注在公开服务方法上。Spring默认通过代理拦截外部调用；同一Bean内部用\texttt{this.method()}自调用不会经过代理，因此方法上的新事务注解不会生效。需要\texttt{REQUIRES\_NEW}时，应把该职责放到另一Bean。

\label{lst:ch05-repository}
\begin{lstlisting}[language=Java,caption={监测记录仓储接口}]
@Service
class AuditService {
    private final AuditRepository auditRepository;
    AuditService(AuditRepository auditRepository) {
        this.auditRepository = auditRepository;
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void record(String action) {
        auditRepository.save(new AuditLog(action, Instant.now()));
    }
}

@Service
class ReadingCommandService {
    private final WaterReadingRepository repository;
    private final AuditService auditService;

    ReadingCommandService(WaterReadingRepository repository,
            AuditService auditService) {
        this.repository = repository;
        this.auditService = auditService;
    }

    @Transactional
    public void save(WaterReading reading) {
        repository.save(reading);
        auditService.record("SAVE_READING"); // 经另一Bean代理调用
    }
}
\end{lstlisting}

主业务是否应与审计记录使用不同事务，取决于失败语义；不能只为展示传播行为而滥用新事务。首次后端课程重点掌握默认传播、回滚规则和事务边界即可。

\subsection{统计量更新}

增量平均值在已有样本数为$n$、均值为$\bar{x}_n$时加入新值$x$，应计算
\[
  \bar{x}_{n+1}=\frac{\bar{x}_n n+x}{n+1}.
\]
计数和均值必须初始化，并在计算后再更新计数。

\label{lst:ch05-tx-service}
\begin{lstlisting}[language=Java,caption={事务服务边界}]
class WaterDataSummary {
    private long dataCount = 0L;
    private double averageLevel = 0.0;

    public void updateStatistics(double newLevel) {
        averageLevel = (averageLevel * dataCount + newLevel)
                / (dataCount + 1);
        dataCount++;
    }
}
\end{lstlisting}

\begin{tipbox}
选学：跨服务一致性可使用事务消息、Saga或补偿流程；DDD聚合可帮助表达复杂一致性边界。这些方法需要结合业务失败语义、幂等和可观测性学习，不作为本章基础代码的必要组成。
\end{tipbox}

\section{服务层与异常处理}

服务层按用例组织方法，例如“保存监测值”“确认告警”“查询测站详情”。输入DTO先通过Bean Validation完成格式校验，领域规则仍由服务或领域对象校验。统一响应不应把所有结果都包装成HTTP 200；HTTP状态码仍须表达协议层结果。

\label{lst:ch05-exception-handler}
\begin{lstlisting}[language=Java,caption={参数校验异常处理}]
record CreateReadingRequest(
        @NotBlank String stationId,
        @DecimalMin("0.0") @DecimalMax("50.0") double level,
        @NotNull Instant measuredAt) {}

@RestControllerAdvice
class GlobalExceptionHandler {
    @ExceptionHandler(EntityNotFoundException.class)
    ResponseEntity<ProblemDetail> notFound(EntityNotFoundException ex) {
        ProblemDetail problem = ProblemDetail.forStatus(404);
        problem.setTitle("资源不存在");
        problem.setDetail(ex.getMessage());
        return ResponseEntity.status(404).body(problem);
    }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    ResponseEntity<ProblemDetail> invalid(MethodArgumentNotValidException ex) {
        ProblemDetail problem = ProblemDetail.forStatus(400);
        problem.setTitle("请求参数无效");
        return ResponseEntity.badRequest().body(problem);
    }
}
\end{lstlisting}

异常处理器把可预期错误转换为稳定契约；意外异常只向客户端返回通用信息，详细堆栈写入受控日志。日志应包含请求标识、测站标识和事件类型，但不得记录密码、完整令牌或敏感个人信息。

\section{Spring Security 6与JWT}

认证回答“用户是谁”，授权回答“允许做什么”。Spring Security 6使用\texttt{@EnableMethodSecurity}启用方法授权，并采用Lambda DSL配置过滤链。无状态API关闭服务器会话并在JWT过滤器中建立认证上下文。

\label{lst:ch05-security-chain}
\begin{lstlisting}[language=Java,caption={Spring Security过滤链}]
@Configuration
@EnableMethodSecurity
@EnableConfigurationProperties(JwtProperties.class)
class SecurityConfig {
    @Bean
    SecurityFilterChain securityFilterChain(HttpSecurity http,
            JwtAuthenticationFilter jwtFilter) throws Exception {
        return http
            .csrf(AbstractHttpConfigurer::disable)
            .sessionManagement(s -> s.sessionCreationPolicy(
                    SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(a -> a
                    .requestMatchers("/actuator/health", "/api/auth/**").permitAll()
                    .anyRequest().authenticated())
            .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class)
            .build();
    }
}
\end{lstlisting}

浏览器若使用Cookie携带凭据，不能机械关闭CSRF防护；上例适用于只从Authorization头读取Bearer令牌的API。权限只使用一个枚举，避免名称和取值漂移。

\label{lst:ch05-jwt-filter}
\begin{lstlisting}[language=Java,caption={JWT认证过滤器}]
enum WaterSystemPermission {
    STATION_READ, READING_WRITE, ALERT_ACKNOWLEDGE
}

@Service
class AuthorizationService {
    void require(Authentication auth, WaterSystemPermission permission) {
        boolean granted = auth.getAuthorities().stream()
                .anyMatch(a -> a.getAuthority().equals(permission.name()));
        if (!granted) throw new AccessDeniedException("权限不足");
    }
}
\end{lstlisting}

JWT密钥通过配置注入并以足够长度的Base64值提供。jjwt 0.11+使用\texttt{parserBuilder()}；刷新令牌即使已过访问式过期点，也应先安全取得Claims，再验证令牌类型、签名、签发者和刷新期限。

\label{lst:ch05-kafka-listener}
\begin{lstlisting}[language=Java,caption={Kafka告警消费者}]
@ConfigurationProperties("security.jwt")
record JwtProperties(String secret, String issuer) {}

@Service
class JwtService {
    private final SecretKey key;
    private final JwtProperties properties;

    JwtService(JwtProperties properties) {
        this.properties = properties;
        this.key = Keys.hmacShaKeyFor(
                Decoders.BASE64.decode(properties.secret()));
    }

    Claims parseAllowExpired(String token) {
        try {
            return Jwts.parserBuilder().setSigningKey(key).build()
                    .parseClaimsJws(token).getBody();
        } catch (ExpiredJwtException ex) {
            return ex.getClaims();
        }
    }
}
\end{lstlisting}

刷新服务必须进一步确认Claims中的\texttt{type=refresh}、签发者和服务端撤销状态，才可签发新令牌对。配置常量由\texttt{JwtProperties}共享，不跨类访问私有常量。

\section{事务事件与消息队列}

同一应用进程内的领域事件可降低模块耦合。若处理必须在数据库事务成功后执行，应使用\texttt{@TransactionalEventListener}并指定\texttt{AFTER\_COMMIT}，不能用普通\texttt{@EventListener}声称“提交后执行”。

\label{lst:ch05-cache-service}
\begin{lstlisting}[language=Java,caption={缓存与分页查询}]
record ReadingSavedEvent(Long readingId, String stationId) {}

@Component
class ReadingEventHandler {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    void afterCommit(ReadingSavedEvent event) {
        metricsCounter.increment(event.stationId());
    }

    private final MetricsCounter metricsCounter;
    ReadingEventHandler(MetricsCounter metricsCounter) {
        this.metricsCounter = metricsCounter;
    }
}
\end{lstlisting}

跨服务通信必须使用网络可达的消息基础设施。下面的Kafka监听器位于告警服务，消费数据服务发布的事件；它不是进程内事件监听器。

\label{lst:ch05-metrics}
\begin{lstlisting}[language=Java,caption={运行指标记录}]
record ReadingMessage(String eventId, String stationId,
                      double level, Instant measuredAt) {}

@Component
class AlertMessageListener {
    private final AlertApplicationService alertService;

    AlertMessageListener(AlertApplicationService alertService) {
        this.alertService = alertService;
    }

    @KafkaListener(topics = "water.reading.saved", groupId = "alert-service")
    void onReading(ReadingMessage message) {
        alertService.evaluateIdempotently(message.eventId(), message.stationId(),
                message.level(), message.measuredAt());
    }
}
\end{lstlisting}

消息系统不能自动保证业务恰好执行一次。生产者应考虑事务外盒（outbox）或可靠发布；消费者用\texttt{eventId}去重，并配置有限重试、死信队列和监控。消息模式适合告警评估、通知和异步统计，不适合需要立即返回结果的简单查询。

在分布式部署中，服务发现负责把逻辑服务名解析为可用实例，配置中心负责管理环境参数，网关负责认证、限流与路由。Spring Boot应用应通过明确的Starter和配置文件接入这些基础设施，并在健康检查中验证注册状态、心跳超时和实例摘除；业务代码只依赖稳定的服务接口，不把具体注册中心的客户端注解扩散到领域层。这样的边界便于在开发、测试和生产环境切换实现。

\section{性能优化与可观测性}

性能优化先测量再修改。数据库查询应建立与查询模式匹配的索引并使用分页；热点且允许短暂陈旧的数据可缓存；外部调用设置连接、读取和总超时；线程池与数据库连接池容量应依据压测结果配置。

可观测性包括日志、指标和追踪。关键指标可包含请求延迟、错误率、数据库连接使用率、Kafka消费积压和告警处理时延。健康检查只说明实例可服务，不等同于业务正确。

\paragraph{后端代码清单导读}
代码清单\ref{lst:ch05-http}至\ref{lst:ch05-metrics}依次覆盖HTTP语义、应用入口、控制器、实体映射、事务、校验、认证、消息消费、缓存和指标记录；读者应从请求进入控制器开始，沿事务与安全边界追踪到数据访问和异步事件。

\section*{小结}

本章从HTTP与REST接口开始，建立Spring Boot配置和分层基础，依次讲解JPA实体、Repository、事务、异常处理、Spring Security 6、JWT、事务提交后事件与Kafka消息。示例统一采用Java 17和Jakarta命名空间，并强调事务代理、幂等、密钥外部化和可观测性等工程边界。

提交一个最小后端原型：测站最新水位查询与监测值写入接口；JPA实体和Repository；一项具有明确事务边界的服务；认证与权限说明；一条提交后事件或Kafka消费链路；以及接口测试和运行日志。
